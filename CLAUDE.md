# CLAUDE.md — unissh

Контекст для AI-ассистентов, работающих с этим репозиторием.

## Что это

**unissh** — терминальный TUI-менеджер VPS-серверов на Go для macOS и Linux (основной
пользователь работает в Warp на macOS). Основной сценарий: открыть утилиту → выбрать сервер
стрелками → Enter → интерактивная SSH-сессия. Второй ключевой сценарий: добавление нового VPS с автоматической первоначальной
настройкой (bootstrap) от root.

Интерфейс **двуязычный (ru/en)**: ВСЕ пользовательские строки живут в `i18n.go`
(структура `L`, инстансы `trRU`/`trEN`, активный язык — глобальный `*L` с именем `T`).
Новую строку добавляй в ОБА словаря с одинаковыми format-плейсхолдерами и используй
только как `T.ИмяПоля` — никаких строковых литералов интерфейса в остальных файлах.
Комментарии в коде — на русском.

## Сборка и проверка

```bash
make build             # fmt-check → vet → test → гейт покрытия → сборка
make test              # go test ./...
make test-race         # тесты с детектором гонок
make cover             # отчёт покрытия
./unissh version       # смоук-тест
```

Один Go-модуль `github.com/MrBenoit/unissh`, два пакета: `internal/app`
(TUI/SSH/OS) и `internal/core` (чистая логика). Тонкий `main.go` в корне. Go ≥ 1.26.

Тесты **есть** и гейтятся: `make build`/CI/релиз не проходят без зелёных тестов и
покрытия `internal/core` ≥ 90% (см. `scripts/coverage.sh`, порог `COVER_MIN`).
Интерактивные модели bubbletea драйвятся в тестах напрямую (`Update`/`View`), а
мастера — через подменяемые `runSelect`/`runInput`/`runMulti` (шов `func`→`var`).
Транспорт SSH проверяется in-process сервером (`sshserver_test.go`).

## Стек

- **UI**: собственные компоненты на `charmbracelet/bubbletea` (главный экран, меню-выбор,
  ввод текста через `bubbles/textinput`, чекбоксы, страницы результата и спиннер) — везде
  мышь+клавиатура, единый полноэкранный стиль. `charmbracelet/lipgloss` (+ `lipgloss/table`)
  для стилей/таблиц. Зависимости от `huh` больше нет.
  **Ничего не печатаем в обычный терминал**: результат действия показывает `showPage`,
  короткое сообщение — `showToast`, ошибку — `showError`, ожидание — `runSpinner`
  (всё в page.go, alt-screen). Исключения по делу: интерактивный `ssh` и `scp` забирают
  tty себе, а поток bootstrap — это последовательный лог.
- **SSH (программный)**: `golang.org/x/crypto/ssh` — bootstrap, инфо, выполнение команд.
- **SSH (интерактивный)**: системный `/usr/bin/ssh` через `exec.Command` (ключ) или через
  `expect` (авто-ввод пароля, см. login.go) — чтобы работали все возможности терминала.
- **Секреты**: системная ключница через CLI (не cgo) — `security` на macOS, `secret-tool`
  (libsecret) на Linux; последний рубеж — JSON-файл 0600.
- **Платформа**: macOS и Linux. Всё системо-зависимое собрано за тремя швами —
  `goos`, `lookPath`, `getenv` (clipboard.go); их подменяют тесты. Никаких build-тегов.

## Данные

- Конфиг: `~/.config/unissh/servers.json` — `{version, settings, servers[]}`.
  У сервера есть стабильный `id` (8 hex) — по нему ключуются записи Keychain,
  поэтому переименование сервера не ломает пароли.
- `settings`: `default_user`, `ssh_key`, `status_timeout`, `language` ("ru"|"en"),
  `bootstrap_defaults` (список ключей шагов настройки — пользовательский дефолт для
  чекбоксов мастера; обновляется при каждом прохождении мастера и правится в Настройках),
  `connect_mode` ("" = новое окно по умолчанию, "inline" = в текущем окне),
  `sort_mode` (""/manual/name/ping/online), `theme` (dark/light/dracula/gruvbox),
  `snippets` (сохранённые команды), `collapsed_folders`. У сервера: `favorite`, `proxy_jump`,
  `last_connected`, `folder`, `tunnels`. Глобалов `gStore`/`gSettings` нет — `*Store`
  передаётся явно по цепочке вызовов.
- **Аутентификация** (`remote.go dialSSH`): ключ (с passphrase из Keychain `passphrase/<путь>`)
  → ssh-agent (`SSH_AUTH_SOCK`) → пароль. Интерактивный ssh (`sshArgs`) поддерживает `-J` (ProxyJump).
- **Бэкапы конфига**: `Save()` снимает снапшот в `backups/` (ротация 20) перед записью;
  восстановление — `restoreBackupMenu` (Инструменты).
- **Инфо при добавлении**: после добавления сервера (bootstrap и обычное) вызывается `actionInfo`
  — подключается и показывает панель, включая ВСЕ адреса интерфейсов (секция `IPS` в `infoCmd`,
  `ip -o addr show scope global`, парсинг в `ipAddrLines`) и загрузку CPU% (секция `CPUSTAT` —
  два замера `head -1 /proc/stat` с паузой 0.3с, `cpuPercentFromStat`, поля user..steal без guest).
- **Открытие ssh** (`connectwin.go`): по `TERM_PROGRAM` выбирается Warp/iTerm/Terminal.
  Warp — новой ВКЛАДКОЙ через tab config `~/.warp/tab_configs/unissh.toml` +
  `open warp://tab_config/unissh` (launch config с `windows:` открывал окно — ушли от него).
  Warpify не настраиваем: Warp сам предлагает варпифицировать, увидев приглашение хоста в
  выводе вкладки. iTerm/Terminal — по-прежнему новым окном (AppleScript). `actionConnect` в
  режиме окна не блокируется на сессии, сразу возвращает в меню; при ошибке — откат к inline.
- **Авто-вход по паролю** (`login.go`): требует `expect` (штатный на macOS). Inline — пароль
  через env `UNISSH_SSHPASS` (не на диске, не в argv), `interact` отдаёт сессию пользователю,
  код выхода ssh пробрасывается. Для нового окна env не доедет через `open`, поэтому пароль
  встраивается во временный скрипт 0600, который сам себя удаляет сразу после `spawn`.
  Ключ подставляется в `send` только по совпадению «password:»/«passphrase» — при неверном
  пароле повтор уходит пользователю (не зацикливаемся). Только auth=password; для ключей — обычный ssh.
- **Главный TUI** (`tui2.go`): bubbletea alt-screen + `WithMouseCellMotion`. `render()` строит
  четыре панели и заполняет `m.regions` (экранный прямоугольник каждой строки) — по ним
  находится клик. Список серверов — строки `listRow` (папка или сервер), см. `tui2_rows.go`.
  Enter/→ на сервере открывает действия, на папке — сворачивает/разворачивает.
  Диалоги (ввод/выбор) не запускаются изнутри TUI: панель возвращает `menuItem` и завершается,
  а `menu.go` выполняет действие — второй `tea.Program` поверх работающего невозможен.
  `space` отмечает серверы; пока карта `m.selected` непуста, правая-верхняя панель показывает
  групповые действия (`curActions()`), а правая-нижняя — список отмеченных вместо статистики.
  Выделение живёт один запуск панели: после группового действия `mainMenu` пересоздаёт модель.
- **Проброс портов** (`tunnels.go`): правила лежат в `Server.Tunnels`, живые процессы — в
  `tunnelManager`. Каждый туннель — `ssh -N` с `ExitOnForwardFailure=yes` в СВОЕЙ группе процессов
  (`Setpgid`), чтобы Ctrl+C терминала не убил его мимо менеджера; гасится сигналом всей группе
  (иначе при парольном входе умрёт `expect`, а его `ssh` останется сиротой). Туннели живут, пока
  жив unissh: `mainMenu` вызывает `StopAll()` на выходе. У `scp` порт — заглавная `-P`, поэтому
  `transfer.go` собирает свои аргументы, а не переиспользует `sshArgs`.
- **Журнал** (`journal.go`): все запуски команд проходят через `runOn`, поэтому запись одна.
  Файл 0600 и в нём МОГУТ БЫТЬ СЕКРЕТЫ из командных строк — не логировать его наружу, не
  копировать в бэкапы, не печатать целиком.
- `auth`: `"key"` или `"password"`. При `password` пароль берётся из Keychain и
  копируется в буфер перед интерактивным подключением (sshpass не используется).
- Отпечатки хостов: `~/.config/unissh/known_hosts` — общий для x/crypto/ssh (TOFU:
  незнакомый хост добавляется, изменившийся — ошибка) и для системного ssh
  (`-o UserKnownHostsFile=... -o StrictHostKeyChecking=accept-new`).
- Экспорт ssh-конфига: `~/.ssh/unissh_config` + строка `Include` в начале `~/.ssh/config`.
  Если файл экспорта существует, он автоматически регенерируется при любом изменении серверов
  (`maybeRefreshSSHConfig`).

## Инварианты bootstrap (НЕ ломать!)

Порядок шагов в `bootstrap.Run()` спроектирован против потери доступа к серверу:

1. Пользователь + ключ ставятся **до** любых изменений sshd.
2. `verifyUserLogin` — реальный вход по ключу с проверкой членства в admin-группе —
   выполняется **до** харденинга. Если не работает, харденинг не начинается.
3. Firewall открывает **и старый, и новый** SSH-порт до смены порта (обе ветки — debian и rhel).
   Дополнительно `configureSSHD` перед сменой порта **best-effort** открывает новый порт
   в ufw/firewalld, даже если шаг «firewall» не выбирался.
4. `configureSSHD`: применить конфиг → `sshd -t` (при ошибке откат) → рестарт →
   **повторный** `verifyUserLogin` на новом порту → при неудаче полный откат конфига
   через живую root-сессию (TCP-сессия переживает рестарт sshd).
   Ошибка `apply()` тоже вызывает `revert()` (конфиг не остаётся в полусостоянии).
5. Харденинг пишется в `/etc/ssh/sshd_config.d/00-unissh.conf` — префикс `00-` обязателен:
   в sshd выигрывает **первое** значение, а cloud-init кладёт свои в `50-cloud-init.conf`.
   Перед перезаписью прежнее содержимое drop-in копируется в `/etc/ssh/00-unissh.conf.unissh-prev`
   (вне `sshd_config.d/`, чтобы не попасть под `Include *.conf`); `revert()` восстанавливает
   именно его — при повторном bootstrap откат не уничтожает прежнюю рабочую конфигурацию.
   Если у системы нет Include — правится основной конфиг: backup через `test -e || cp`
   (не `cp -n`, который на coreutils≥9.2 даёт код 1); sed удаляет прежние директивы только
   **до первого Match-блока** (`/^[Mm]atch /,$!{...}`) и вставляет свои в строку 1.
6. Ubuntu 22.10+: порт слушает `ssh.socket` — перед сменой порта socket отключается,
   включается `ssh.service`. RHEL: `semanage port` best-effort.
7. Пароль пользователя передаётся `chpasswd` **через stdin**, не в командной строке, и
   сохраняется в Keychain **сразу** после успешного `chpasswd` (колбэк `bootstrap.onPassword`,
   выставляется в `runBootstrapAndSave` для существующего сервера). При аборте после `chpasswd`
   пароль показывается пользователю (`result.Password` возвращается даже при ошибке) — иначе
   новый пароль был бы утерян, а старый в Keychain стал бы нерабочим.
8. SSH-ключ добавляется в `authorized_keys` **через stdin** (`$KEY=$(cat)` в `authKeyInstallScript`),
   не через `echo '...'` — комментарий в .pub может содержать кавычки и сломал бы shell.
9. Критические шаги (юзер, ключ, проверка входа) прерывают настройку; остальные
   (обновление, fail2ban, swap…) добавляют предупреждение и продолжают.
10. Повторный bootstrap (`rebootstrapFlow`) для настроенного сервера предлагает root-доступ
    **по ключу первым** — после харденинга парольный вход root отключён, но ключ root установлен.

Дистрибутивы: Debian/Ubuntu (`apt`, группа `sudo`, ufw) и RHEL-семейство
(`dnf`/`yum`, группа `wheel`, firewalld). Прочие — только юзер+ключ, с предупреждением.

## Конвенции кода

- Все интерактивные вопросы — через хелперы `ask*` из `ui.go`; проверяйте второй
  возвращаемый `ok` (false = Esc/Ctrl+C → мягкая отмена текущего мастера, не падение).
- Строки интерфейса — только через `T.*` (см. выше про i18n.go).
- Пользовательские строки в командную строку удалённого шелла попадают только после
  валидации регекспами (`usernameRe`, `tzRe`, `hostnameRe`); произвольные данные —
  через stdin (`Run(cmd, stdin, ...)`) или `shellQuote`.
- Публичный ключ добавляется в `authorized_keys` через stdin (`authKeyInstallScript`),
  а не через `echo '...'` — .pub-комментарий может содержать кавычки.
- Удалённые команды оборачиваются в `LANG=C LC_ALL=C sh -c '...'` (парсинг вывода
  рассчитан на английскую локаль). Любой вывод сервера перед печатью в локальный
  терминал проходит через `sanitizeRemote()` (срезает ANSI/управляющие последовательности).
- Цвета — только из констант палитры в `theme.go`.
- `Store.MustSave()` после каждой мутации конфига; `maybeRefreshSSHConfig(st)` после
  изменения списка серверов.
- Пользовательские экраны рисуются только через page.go (`showPage`/`showToast`/`showError`/
  `runSpinner`), а не через `fmt.Println` + `pressEnter`/`time.Sleep`: иначе alt-screen
  схлопывается и результат оказывается в обычном терминале.
- `runSpinner` всегда дожидается завершения fn (`<-done`), даже при Ctrl+C — иначе
  осталась бы горутина и гонка за результатом. Прерывание возвращается как ошибка.
- Открытие соединения с запросом пароля (`openRemote(s, true)`) должно быть **вне**
  `runSpinner`/`runPage` — форма пароля и страница не могут делить один tty.
- Таблицы строятся только через `newTable(headers…)`; общие опции ssh/scp — через
  `sshCommonArgs(s)`; пароль сервера — только через `serverPassword(s)`.
- Тесты подменяют `runPage`/`runToast`/`runSpinner` в `TestMain` — у `go test` нет tty.
  Строки i18n охраняет `i18n_test.go`: ни одного пустого значения, плейсхолдеры ru/en совпадают.
- `~/.ssh/config` и `~/.ssh/unissh_config` пишутся атомарно (`writeAtomic`), значения
  экранируются (`sshConfValue`); `maybeRefreshSSHConfig` НЕ восстанавливает удалённую
  строку Include (навязывание только через явный «Экспорт»).

## Известные ограничения / идеи

- **ssh-agent и ключи с passphrase**: `remote.go` использует ssh-agent (`SSH_AUTH_SOCK`) и
  passphrase из Keychain (`keyAuthMethod`). Интерактивного запроса passphrase пока нет —
  зашифрованный ключ без агента/кэша не подключится (программный клиент).
- **ProxyJump**: поддержан и в интерактивном ssh (`sshArgs -J`), и в программном клиенте
  (`dialSSH`/`dialViaJump` через бастион). Бастион аутентифицируется тем же ключом/агентом.
- Пакеты: `internal/app` (TUI/SSH/OS, `package app`) и `internal/core` (чистая
  логика без зависимостей от TUI/i18n, тесты ≥90%), тонкий `main.go` в корне.
  Подменю (add/tools/manage) используют собственные bubbletea-компоненты (select/input/multiselect);
  их обёртки `runSelect`/`runInput`/`runMulti` — `var`, чтобы мастера тестировались без TTY.
- Кроссплатформенность: macOS и Linux. Платформенное — в `clipboard.go` (швы `goos`/`lookPath`/`getenv`),
  `secrets.go` и `connectwin.go`. `osascript`/Warp — только macOS; на Linux новое окно
  открывается через `$TERMINAL` или белый список эмуляторов, а при их отсутствии
  `connectInNewWindow()` возвращает false и мы честно подключаемся inline.
- Live-монитор требует Linux на сервере (/proc); BSD не поддержан.
- `unissh list` работает без TTY; остальное требует интерактивный терминал.
- **Keychain через argv (только macOS)**: `secretSet` вызывает `security add-generic-password -w <пароль>` —
  на короткое время пароль виден в `ps` локальному пользователю (у macOS CLI `security`
  нет неинтерактивного способа подать секрет через stdin). Приемлемо для однопользовательского
  Mac; если понадобится ужесточить — писать через Security framework (cgo) или временный fd.
